**4:10–5:25 — Technical architecture and failure.**

### Presenter recovery ladder, prepared before taking the stage

1. **Model slow or unavailable:** “Open dialogue is unavailable. This is the authored explanation; the next state change is still live.” Keep the learner action visible. Do not read a plausible model response aloud while waiting as if it arrived.
2. **Network unavailable:** If actual local execution has been checked: “This downloaded episode is running locally. New dialogue and new downloads are unavailable.” A first-load failure is possible; do not promise an offline first visit.
3. **Local app fails:** “We cannot execute the new input here. This is a recording of an earlier run.” Keep a large recording label and fixed inputs visible. If no real earlier recording exists, use a labeled storyboard and explicitly state no technical proof is being shown.

The “magic” that survives is that the learner's action still changes a meaningful situation. It is not a theatrical substitute for a failed model. A local failure loses that magic; the pitch must accept the lost demonstration credit.

## Revision record and reversal conditions

**R04.1 → R07.0 latency/outage critique → R07.1 stateful practice with optional dialogue.** Only this rehearsal document changed. The revision removes any implication that continued animation equals continued intelligence. It specifies the useful subset without a model, forbids silent replay of answers, binds responses to state revisions, distinguishes simulated fault injection from a real network outage, and requires fallback recordings to remain visibly recordings. It preserves learner agency and the narrower buyer hypothesis from R04.1.

Reverse toward **A** when observed post-Claude checking, assembly or permission work is frequent and consequential, and a fictional-data prototype can remove that specific burden without bypassing access boundaries. Reverse toward **B** when a buyer has a recurring unresolved choice, needs people to try alternatives during a conversation, and current tools demonstrably leave that decision waiting. Reverse away from **C** if authoring/review dominates benefit, expert approval is unavailable, the exercise teaches overconfident false rules, learners cannot use it without avoidable interface friction, the only buyer wants hiring screening, or dialogue contributes no value beyond the fixed activity. In the last case, simplify the mechanism before claiming an AI business.

For the competition specifically, a failure to execute the changed-input consequence removes C's key proof; a storyboard or recording does not restore live-input credit. An honestly smaller functioning prototype can still be preferable to a wider broken one, but today every prototype here remains proposed.
